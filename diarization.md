# Cross-Session Voice Biometrics (Speaker Recognition)

Архитектура «Apple Photos для голосов» на базе текущего движка `FluidAudio`. 

> ## 🔎 REALITY CHECK (сверка с реальным кодом — FluidAudio 0.14.7, ветка `dev`)
>
> **Вердикт: премиса жизнеспособна, но док врёт в деталях и молчит про дыры.**
>
> Главное, что подтвердилось: FluidAudio **реально отдаёт эмбеддинги и базу спикеров** — `DiarizationResult.speakerDatabase: [String:[Float]]?` (`DiarizerTypes.swift:125`) и `TimedSpeakerSegment.embedding: [Float]` (256-мерный, `DiarizerTypes.swift:147`, `SpeakerManager.swift:12`). Так что вытащить вектора можно.
>
> Но 4 фундаментальных расхождения, которые надо знать ДО старта:
> 1. **Не та модель.** Приложение использует `OfflineDiarizerManager` (`main.swift:757,769`) на пайплайне **pyannote community-1** (`OfflineDiarizerTypes.swift:30`), а НЕ онлайновый `DiarizerManager`/`WeSpeaker`, как пишет док. Эмбеддинги — pyannote-стиля, и в комплекте идёт **PLDA-модель** (`pldaRhoPath`, `OfflineDiarizerModels.swift:111`) — т.е. «родная» метрика тут PLDA, а не косинус.
> 2. **Rust выбрасывает всю структуру.** `FluidAudioOutput` десериализует **только `{ model, text }`** (`transcription.rs:48`) — `segments` и `speakerCount` дропаются, метки спикеров живут только строкой внутри `text`. `TranscriptJson` тоже хранит только `text`, без сегментов. Структурных данных о спикерах на стороне приложения сейчас **нет вообще**.
> 3. **UI переименования спикеров не существует.** Ни команды `tag_speaker`, ни редактора спикеров, ни `speakers.json`. Шаг 2.4 — это не «допиши», а целая новая фича.
> 4. **Приватность.** Голосовые слепки — биометрия. Для «privacy-first» приложения хранить их открытым JSON в `~/.nbp` без согласия/удаления/версии модели — отдельный разговор.
>
> Детальные пометки — под каждым шагом ниже (`> 🔎`).

## 1. Концепция: KNN (K-Nearest Neighbors) вместо усреднения
Мы **не** усредняем вектора (эмбеддинги) одного и того же человека. Усреднение векторов с разных микрофонов или из разных акустических сред (комната vs машина) создает «мертвую зону» в векторном пространстве, которая не похожа ни на один из оригинальных голосов.

Вместо этого мы храним **список векторов** для каждого человека. 
- Саня с AirPods -> Вектор 1
- Саня с Mac -> Вектор 2
При матчинге нового звонка мы считаем `Cosine Similarity` между новым голосом и **каждым** вектором в нашей базе. Максимальное совпадение побеждает. 

> 🔎 **Реальность:** идея здравая. Но учти: у FluidAudio УЖЕ есть свой механизм — `SpeakerManager.findSpeaker(with:speakerThreshold:)` + `embeddingThreshold` + `Speaker.mergeWith(...)` (`SpeakerManager.swift:184`, `DiarizerManager.swift`). Он живёт **в пределах одного процесса** и не персистится между запусками — поэтому свой кросс-сессионный стор оправдан. Но не «изобретай косинус с нуля» вслепую: метрика, под которую обучен оффлайн-эмбеддер, — **PLDA**, а не косинус (см. шаг 2.3).

## 2. Шаги по реализации

### Шаг 2.1: Вытаскиваем вектора из Swift-сайдкара
Разработчик библиотеки `FluidAudio` уже собирает биометрические слепки (d-vectors) через модель `WeSpeaker` внутри `DiarizerManager` и отдает их наружу.

> 🔎 **Реальность:** ⚠️ **WeSpeaker / `DiarizerManager` — это онлайновый путь, который приложение НЕ использует.** Мы на `OfflineDiarizerManager` (`main.swift:757`), модель — pyannote community-1. Но финал тот же: оффлайн-`process()` **сам строит** `speakerDatabase` через `reconstruction.buildSpeakerDatabase(segments:)` и возвращает его (`OfflineDiarizerManager.swift:331,351`). Комментарий в либе прямо говорит: *«Speaker database with embeddings (populated by offline pipelines for downstream use)»* (`DiarizerTypes.swift:124`). То есть `result.speakerDatabase` тут **непустой** — бери его и не выдумывай фолбек.

В файле `fluidaudio-sidecar/Sources/main.swift`:

1. Добавь поле в JSON-структуру:
```swift
struct FluidAudioOutputJSON: Codable {
    let text: String
    let speakerCount: Int
    let model: String
    let segments: [SpeakerSegment]
    // НОВОЕ ПОЛЕ:
    let speakerProfiles: [String: [Float]]?
}
```

> 🔎 **Реальность:** ✅ структура совпадает с реальной (`main.swift:13`). Сейчас она строится в одном месте около `main.swift:898` (`FluidAudioOutputJSON(text:..., speakerCount:..., model:..., segments:...)`) — туда и прокидывай `speakerProfiles: diarizationResult.speakerDatabase`. Кодировщик стоит с `.sortedKeys` — на парсинг в Rust не влияет.

2. Внутри функции, где формируется `FluidAudioOutputJSON` (ближе к концу файла `main.swift`), прокинь словарь из `DiarizationResult`. Если `FluidAudio` не отдает `speakerDatabase` напрямую, ты можешь собрать центроиды сам из `TimedSpeakerSegment`:
```swift
// Грубая сборка профилей из результатов:
var profiles: [String: [Float]] = [:]
// Если FluidAudio отдает speakerDatabase, бери оттуда:
if let db = result.speakerDatabase {
    profiles = db
} else {
    // Иначе усредни эмбеддинги для каждого спикера внутри ТЕКУЩЕГО звонка
    // (внутри одного звонка усреднять можно, микрофон один и тот же)
    for seg in diarizationSegments {
        // Усреднение или просто сохранение первого вектора
        profiles[seg.speakerId] = seg.embedding 
    }
}
```

> 🔎 **Реальность:** ⚠️ две придирки. (1) Фолбек **не нужен** — оффлайн-путь всегда заполняет `speakerDatabase`. (2) Сам фолбек-код врёт: коммент говорит «усредни», а строка `profiles[seg.speakerId] = seg.embedding` просто **перезаписывает** последним сегментом (last-wins), никакого усреднения. Если уж делать фолбек — накапливай и дели, но проще выкинуть `else`-ветку целиком. И помни: важна стабильность **версии модели** — кросс-сессионный матчинг ломается, если апдейт FluidAudio сменит эмбеддер (см. ниже про версионирование).

### Шаг 2.2: Принимаем вектора в Rust бэкенде
В файле `src-tauri/src/transcription.rs` (где парсится `FluidAudioOutput`):

1. Обнови структуру десериализации:
```rust
#[derive(Deserialize, Debug)]
struct FluidAudioOutput {
    model: String,
    text: String,
    // НОВОЕ ПОЛЕ:
    #[serde(default)]
    speakerProfiles: Option<std::collections::HashMap<String, Vec<f32>>>,
}
```

> 🔎 **Реальность:** ✅ `struct FluidAudioOutput { model, text }` совпадает 1-в-1 (`transcription.rs:48`). НО:
> - ❌ **Не скомпилируется как написано.** Поле `speakerProfiles` (camelCase) ловит `non_snake_case`, а у репо `clippy -D warnings` — это ошибка сборки. Правильно: `#[serde(rename = "speakerProfiles")] speaker_profiles: Option<HashMap<String, Vec<f32>>>` (или `#[serde(rename_all = "camelCase")]` на структуре).
> - ⚠️ **Парс-сайтов два:** `transcription.rs:252` (он переиспользуется и для Apple Speech) и `transcription.rs:356` (FluidAudio). Профили придут только из FluidAudio-ветки (~356). Диктовка всегда с `--no-diarize` (`transcription.rs:282`) → профилей там нет вообще.
> - ⚠️ **Главное:** сегменты/спикеры сейчас **нигде структурно не сохраняются** — `TranscriptJson` (`transcription.rs:55`) держит только `text`. Так что без шага «сохранить профили на диск» (ниже) данные просто потеряются после транскрипции.

2. Внутри `TranscriptionProvider::FluidAudio` блока, после десериализации `let out: FluidAudioOutput = ...`, сохрани `out.speakerProfiles` куда-нибудь (например, в отдельный JSON-файл рядом с транскриптом: `recording_dir.join("speakers.json")`).

> 🔎 **Реальность:** ✅ разумно и необходимо (иначе вектора негде взять при позднем переименовании). Учти retention: авто-удаление сносит файлы записи, но **сохраняет `pipelines/`** — `speakers.json` ляжет в корень записи и будет удалён вместе с аудио. Если слепки нужны дольше записи — копируй вектор сразу в глобальную базу (шаг 2.4), а не полагайся на per-recording `speakers.json`.

### Шаг 2.3: Векторная база и Матчинг (`storage.rs`)

1. Создай глобальный файл `~/.nbp/known_speakers.json`:
```json
{
  "Саня": [
    [0.15, -0.42, 0.88, ...], 
    [-0.11, 0.05, 0.33, ...]
  ],
  "Юля": [
    [0.89, 0.12, -0.44, ...]
  ]
}
```

> 🔎 **Реальность:** ✅ `~/.nbp/` — это `get_config_dir()` (`config.rs`), там уже лежит `settings.json`. Векторы 256-мерные. ⚠️ Добавь в формат **тег версии эмбеддера** (модель + версия FluidAudio), иначе после апдейта модели старые слепки станут мусором и начнут давать ложные матчи. И ⚠️ это **биометрия открытым текстом** в незашифрованном JSON — для «privacy-first» приложения нужен явный консент + удаление + запрет на синк.

2. Напиши простую функцию Косинусного сходства (Cosine Similarity):
```rust
fn cosine_similarity(a: &[f32], b: &[f32]) -> f32 {
    let dot: f32 = a.iter().zip(b).map(|(x, y)| x * y).sum();
    let norm_a: f32 = a.iter().map(|x| x * x).sum::<f32>().sqrt();
    let norm_b: f32 = b.iter().map(|x| x * x).sum::<f32>().sqrt();
    dot / (norm_a * norm_b)
}
```

> 🔎 **Реальность:** ⚠️ функция корректна, но добавь guard на `norm_a*norm_b == 0.0` (пустой/тихий сегмент → `NaN`). Глубже: оффлайн-пайплайн поставляет **PLDA-модель** (`OfflineDiarizerModels.swift:111`) — эмбеддинги pyannote сравниваются через PLDA, а не голый косинус. Косинус «сработает приблизительно», но это не та метрика, под которую заточена модель.

3. **Логика матчинга на новом звонке:**
Когда транскрипция завершена, пройдись по всем полученным `speakerProfiles`. Для каждого профиля `X`:
- Посчитай `cosine_similarity(X, Y)` для **всех** известных векторов `Y` в базе.
- Найди максимум.
- Если `max_similarity > 0.82` (порог нужно оттюнить, зависит от WeSpeaker, обычно от 0.75 до 0.85), то переименуй все вхождения этого спикера в `out.text` и `out.segments` на имя найденного человека.

> 🔎 **Реальность:** ❌ **Порог 0.82 «от WeSpeaker» — не от той модели.** Тут pyannote + PLDA, и WeSpeaker-овые 0.75–0.85 сюда не переносятся — калибруй с нуля на своих данных. ❌ **`out.segments` на стороне Rust НЕ существует** — десериализуется только `text`. Переименование = строковая замена в `text` + ре-рендер `transcript.md`. ⚠️ И спорь с собой про false-positive: один порог на всех = чужие голоса начнут клеиться к знакомым именам; нужна логика «несколько кандидатов близко → не уверены → оставить Speaker N».

### Шаг 2.4: Обучение базы (UI -> Rust)
Когда юзер видит в UI `"Speaker 2"` и вручную переименовывает его в `"Саня"`:
- Фронтенд отправляет команду в Rust: `tag_speaker(recording_id, "Speaker 2", "Саня")`.
- Rust открывает локальный `speakers.json` конкретного звонка, достает вектор для `"Speaker 2"`.
- Rust открывает глобальный `known_speakers.json` и делает `push()` этого вектора в массив `"Саня"`. 
- Готово. Нейронка стала умнее.

> 🔎 **Реальность:** ❌ **Этого UI нет.** Ни `tag_speaker`, ни редактора спикеров, ни структурного представления спикеров во фронте — метки `Speaker N` сейчас просто вшиты строкой в `text` транскрипта (`detail.js` рендерит plain text). То есть Шаг 2.4 — это **полноценная новая фича**, а не «допиши команду»: нужен (а) структурный показ спикеров в детали записи, (б) inline-rename UI, (в) команда `tag_speaker`, (г) per-recording `speakers.json` с векторами, (д) ре-рендер транскрипта после переименования. Это самый большой кусок работы, а док подаёт его как тривиальный финал.
>
> ⚠️ И ещё: `push()` без дедупликации раздует базу (каждое подтверждение = +1 вектор). Нужен лимит K на человека / отбрасывание почти-дубликатов, иначе матчинг со временем замедлится и «размажется».
